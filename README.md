# AniBeam

AniBeam is an anime discovery app drawn like a manga page. It shows what's trending, lets you search and browse by decade, and pulls a random title from a gacha machine. Each title tints the page in its own cover color. Live chat about episodes is planned for a later phase. Anime data comes from the [AniList GraphQL API](https://docs.anilist.co/). AniBeam is not affiliated with AniList.

> Phase 2, the design phase, and Phase 4, My List, are complete (see [Phase 2 complete](#phase-2-complete) and [Phase 4 complete](#phase-4-complete)). The app is a Discover page: an intro, this week's trending titles as a manga page, a random pull, titles by decade, and search. Every title has its own address, where it opens in a full-screen title card with its banner, synopsis, tags and trailer, and Save, Want to try and Favorite, which this browser remembers and the My List page at `/list` shows, linked from the header, the phone's menu and the intro (see [My List](#my-list)). Mood sliders, live chat and sync come next, in Phases 5 to 8.

## Prerequisites

- Node.js 22.18 or newer (`node -v`). The tests run TypeScript files directly, which older versions can't do.
- npm 10 or newer

## Setup

```bash
npm install                                   # installs all workspaces
cp web/.env.example web/.env.local            # frontend config (optional for now)
cp server/.env.example server/.env            # chat server config (optional for now)
```

The `.env.example` files list every variable with a comment explaining it. Real `.env` files are gitignored, so never commit them.

## Scripts (run from the repo root)

| Command                | What it does                                                           |
| ---------------------- | ---------------------------------------------------------------------- |
| `npm run dev`          | Starts the web app at http://localhost:5173                            |
| `npm run dev:server`   | Starts the chat server at http://localhost:3001 (`GET /health`)        |
| `npm run build`        | Type-checks and builds every workspace                                 |
| `npm run typecheck`    | Type-checks every workspace                                            |
| `npm run lint`         | Lints the web app with oxlint, which refuses `dangerouslySetInnerHTML` |
| `npm test`             | Runs the unit tests with Node's built-in test runner                   |
| `npm run test:browser` | Runs the browser checks in `web/e2e` (see below)                       |
| `npm run format`       | Formats the repo with Prettier                                         |

`npm test` and `npm run test:browser` stop a test after its time limit, and end each test file's process the moment its last test ends, so that a test left waiting can't stall them. Each file's results reach the runner through a pipe, which macOS writes in the background, so a process ended that way could lose the last of them, and a run passed on fewer tests (270 of 303 once). So every test process writes its output at once (`web/scripts/blocking-test-output.ts`), and a reporter fails the run, naming the file, if any test a file queued never reported (`web/scripts/every-test-reported.ts`). A file queues every test as it loads only if it awaits nothing at its top level after its first test, and a test holds every test file to that: a test registered after such an await would never be queued, and could go missing unseen.

## Deploying

The site deploys on [Vercel](https://vercel.com). Sign in with GitHub and import this repository. Vercel finds two apps, `web` and the Fastify chat server, so import only `web`. Vercel then uses its Vite settings with `web` as the root directory. It installs the workspaces, runs `npm run build`, and serves `dist`. No environment variables are needed yet. `web/vercel.json` sends every address that is no file to `index.html`, so a title's own address, such as `/anime/154587`, reaches the app instead of Vercel's 404 (see Title addresses). `npm run dev` and `vite preview` do that on their own, so only a unit check (`web/src/app/vercel.test.ts`) can catch the rule going missing.

After that, every pull request gets a preview link, and merging into `main` updates the live site. The chat server will need a host that keeps WebSocket connections open, which is planned for Phase 6.

```
│       │   ├── anime/       #   AniList queries and display helpers
│       │   ├── theming/     #   Adaptive accent color (deriveAccent, CSS variables)
│       │   ├── mood/        #   The gacha pull machine; mood sliders and scoring come later
│       │   ├── list/        #   Saved list (Saved / Want to try / Favorite)
│       │   ├── chat/        #   Live chat UI
│       │   └── sync/        #   Cross-device sync (stretch goal)
│       ├── components/      # Shared UI from the chosen design: header, panels, title card
│       ├── prototype/       # Design prototypes, development only (?variant=A|B|C|D)
│       ├── gallery/         # Component gallery, development only (?gallery)
│       ├── lib/             # Low-level clients and helpers (AniList client, query cache, the address, Firebase)
│       ├── styles/          # Tailwind entry point, design tokens, custom CSS
│       └── main.tsx         # Entry point
├── server/                  # Chat API: Fastify + Socket.IO + Postgres
│   └── src/
│       ├── routes/          # REST endpoints (e.g. message history)
│       ├── sockets/         # Socket.IO event handlers (join room, send message)
│       ├── db/              # Database schema, migrations, client
│       ├── auth/            # Firebase sign-in token verification
│       ├── moderation/      # Rate limits, reports, profanity filter
│       └── index.ts         # Entry point
├── shared/                  # Types and validation schemas used by both web and server
│   └── src/
└── package.json             # Workspace root and shared scripts
```

Empty folders hold a `.gitkeep` file so git tracks them; each one is removed once real code lands in that folder. Unit tests live next to the code they test (`*.test.ts`). The browser checks live in `web/e2e` (`*.e2e.ts`).

## Notes

### AniList requests

The browser calls AniList directly, so each visitor's IP address gets its own limit of 30 requests a minute. `web/src/lib/anilist.ts` holds every request back for up to a minute after a 429, after a failed connection, or when AniList reports no requests left. Failed connections wait too, because a rate-limit reply without CORS headers reaches the browser as a plain network error. When AniList says when the limit resets, the wait ends up to 2 seconds after that, at random. Devices on one network share one IP address, and so one limit and one reset time, and this keeps them from all asking again in the same instant.

TanStack Query saves results in `localStorage` (`web/src/lib/queryClient.ts`): a list for a day, and a title asked for at its address for a day while it airs, or for 30 days once AniList says it has finished, as its details won't change (spec §3H). When a refresh fails, the last good list stays saved. It caches each result under its exact query text and variables, so editing a query never shows results saved for the old version, and a saved copy brings none of them back. So a release that changes a query drops what returning visitors saved under the old one, once: as the lists begin to carry each title's trailer, every list's query changes, so a visitor back within a day of their last visit loses the lists saved then: the page asks AniList for them again, and while AniList is down shows the samples, as on a first visit. `web/e2e/outage.e2e.ts` holds that to the last release's query text, written out, and checks that a copy saved under today's comes back through the page's own persister. Each result comes back only while it is kept (`keptFor` in `web/src/features/anime/queries.ts`), counted from when AniList sent it, not from when the copy was last saved, which happens whenever anything in it changes. Each save writes out the whole copy, which a day of searches can grow to megabytes (150 searches make 3.7 million characters; a finished title kept 30 days adds about 3,000, and only one opened at its address): it waits for the page to draw what just arrived (its next frame, then just after it), so a search's titles never wait for it. In a hidden tab, which draws nothing, it goes at once, and so does one still waiting as the tab is hidden, as closing it does first. Change `buster` in `queryClient.ts` only if the code that reshapes results changes.

Saved trending titles are refreshed once they are over 30 minutes old. If the refresh brings a new order while the trending panels or the intro's covers are on screen, they keep the order the visitor is looking at until they are scrolled away, so nothing reshuffles in front of the visitor (`web/src/lib/steadyList.ts`).

### Reduced motion

Visitors who ask for reduced motion get no sliding, zooming or swinging. They can ask on their device, which the browser reports as `prefers-reduced-motion`, or on the site, with the Reduce motion switch in the footer, above AniList's credit.

The switch is a native checkbox with `role="switch"`, in `web/src/components/MotionSwitch.tsx`. On, it sets `data-motion="reduce"` on `<html>`, which every motion rule and script obeys, and saves the choice as `localStorage['anibeam:motion'] = 'reduce'`. Off, it takes both away, and motion comes back without the page playing its entrances again: the animations that come back with it finish at once, at their last frame, so nothing already on the page moves, while what arrives later, such as the next pull, moves as usual. On a later visit, `web/src/main.tsx` puts a saved choice back on `<html>` before React draws anything, so no entrance plays. If storage is blocked or full, the choice lasts for the visit only.

The switch can only reduce motion. It stops motion on a device that allows it, but it can't bring motion back while the device asks for reduced motion. While the device asks, the switch shows on and locked (yellow, flat and dashed), with the line "On because your device is set to reduce motion." It stays focusable, with `aria-disabled` instead of `disabled`, so a screen reader reaches it and hears that line. A click or Space changes nothing, and a choice saved on an earlier visit stays saved for when the device stops asking. The switch follows the device's setting as the visitor changes it, with the page open. When the device stops asking, motion comes back the same way.

The switch comes after every title on the page, so a second skip link, "Skip to Reduce motion", follows "Skip to content". Like the first, it shows only while it has focus. It links to the switch's checkbox, `#reduce-motion`, the one part of the switch that can take focus. So from the top of the page, Tab, Tab and Enter put the focus on the switch, ready for Space.

#### One source of truth

The site's setting lives in one place, `data-motion="reduce"` on `<html>`. Styles and scripts read it there, together with the device's setting.

In the app's scripts, `web/src/lib/motion.ts` is the one place that asks the device:

- `reducedMotion()` is true when `<html>` has `data-motion="reduce"` or the device asks for reduced motion. A script that moves anything asks it each time it is about to move, as the pull's reveal does.
- `deviceReducesMotion()` and `watchDeviceMotion()` read the device's setting alone and follow its changes, for the switch's locked state, and so that a title card playing its way back closes at once if the device starts asking for reduced motion.
- `savedMotionChoice()` and `saveMotionChoice()` read and write the saved choice, in try/catch.
- `finishEntrances()` finishes the animations that motion coming back on starts over, on the page's own clock only: the splash cover's drift follows the scroll, and transitions such as the switch's knob run on.
- `watchMotionBackOn()` calls back each time motion comes back on, by the switch or on the device, before the browser draws a frame of it, and the switch has it finish the entrances then. It watches the size of `.ab-motion-sentinel`, a box in the footer that no one sees, which the motion gates widen from 1px to 2px: a ResizeObserver calls back after layout, before the frame is drawn, while the media query's change event comes a frame late in Chrome.

In the styles, every motion rule sits in one of the motion gates in `web/src/components/components.css`, written like this:

```css
@media (prefers-reduced-motion: no-preference) {
  :where(:root:not([data-motion='reduce'])) {
    /* what motion adds */
  }
}
```

The media query hears the device, and the `:where()` rule holds only while the site's setting is off. `:where()` adds no specificity, so the rules inside keep their rank. The production build writes the nesting out as plain selectors, for browsers that can't read nesting.

The calm look is every rule's default, and a gate adds the motion. Motion that needs another condition, such as a width, nests it inside the `:where()` rule. Rules for `<html>` itself, such as smooth scrolling, go in `& { … }` inside the `:where()` rule, which matches `<html>`: nested there as `html { … }` or `:root { … }`, a rule reaches only what lies inside `<html>`, so it never applies. Never write a rule under `@media (prefers-reduced-motion: reduce)`, and don't use Tailwind's `motion-safe:` or `motion-reduce:` variants: a media query hears only the device, so the switch can't reach them. Tailwind's motion utilities, such as `animate-spin` or `hover:-translate-y-1`, can't sit in a gate at all, as Tailwind writes their rules outside it, and neither can a transition or an animation in a `style` prop: give the element an `ab-` class, and its motion a rule in a gate.

`npm test` holds the app to this. `web/src/components/motion.test.ts` reads every stylesheet in `web/src` but the development-only prototypes'. Outside the gates, it fails on a transition that names a property that moves or resizes a box, or `all`, or that names none, which means all, as `transition: 0.2s` does; on a hover or press rule that sets such a property; on an animation other than a fade of 150 ms or less that plays once; on smooth scrolling; and on a rule that pauses an animation (a paused animation outside the gates would hold its frame for good). The properties that move or resize a box are `transform`, `translate`, `rotate` and `scale`, any width or height, `top`, `right`, `bottom`, `left` and `inset`, and margins and padding, with their longhands and prefixed names. A `var()` in a transition outside the gates reads as each value a rule there sets its custom property to, and as its fallback; one with neither fails, as the check can't read it. It also fails on a rule in a gate but outside its `:where()` rule, on a rule in the `:where()` rule that names `html` or `:root`, and on a rule that asks the device about motion outside a gate. `web/src/lib/motion.test.ts` reads the app's scripts and stylesheets, all but the tests and the prototypes, and `web/index.html`. It fails on any line of code in a script other than `lib/motion.ts` that names `prefers-reduced-motion`; on Tailwind's motion variants; on its motion utilities in a class name, in the markup or after `@apply` (`animate-…`, `transition`, `duration-…`, `scroll-smooth`, `translate-…`, `rotate-…`, `scale-…` and `skew-…`, under a variant or not); and on a `style` prop that sets a transition, an animation or `scroll-behavior`. The browser checks run the reduced-motion group twice, once with the device asking and once with the site's setting on, and load the page with the choice saved. In both, a walk through every part that moves, on a desktop and a phone, must start no animation or transition that moves or resizes, by CSS or the Web Animations API, only fades and changes of color, listening for at least 500 ms after each step, so that one starting late is heard, and 1 s after each step leave none on the page: the scroll slam and the links docking, the decade strip scrolled sideways, a search, a title's card with its band, details and banner (the step waits for the banner to load or fail), Read more and the spoiler tags, the trailer and Esc out of it and the card, a pull, the phone's header hiding and coming back, the menu by its button and Esc and by a swipe and a drag, and the search bubble growing and folding. ### Landing (the scroll slam)

Parts of the page land once, as they scroll into view: the trending panels, the decade and search cards, the pull machine and the section headings. The intro, the splash cover's drift, the title card and the pull's reveal play as before. A part waits, see-through in its place, until 15% of it shows, then slams in: a trending panel as solid ink from 1.14 times its size and turned 2.5 degrees, then its ink wipes off, its cover settles and its caption pops; a card pops in; the machine drops in; a heading's sound effect booms. Parts that come into view together land one after another, in reading order, 90 ms apart (cards 60 ms), and a card scrolled into view sideways lands then. After that nothing moves again: scrolling back replays nothing, and neither does a refresh that moves a panel. Keyboard focus lands a part at once, but a heading reached through a header link or an intro button, or handed focus by Try again, booms as it takes focus, and a printed page shows every part. Under reduced motion, from the device or the switch, nothing waits and nothing moves.

`web/src/lib/landing.ts` decides when: one IntersectionObserver, a MutationObserver that finds parts as titles load and lists change (before the browser draws them), and a focus listener. Each part carries `data-land`: `wait`, `go` while its slam plays, then `done`, with no animation left. The Landing section of `web/src/components/components.css` does the moving, inside the motion gate. The knobs, `--slam-scale`, `--slam-tilt` and `--slam-stagger`, are tokens in `web/src/styles/index.css`. A part showing by less than 15% lands once it has stayed in view 0.2 s, and a part lands as it shows below the sticky header, not under it, or at the screen's top while a phone's header is hidden. `web/e2e/landing.e2e.ts` checks it: nothing 15% on screen waits, a sliver lands after a moment, each part slams once and shows in time, nothing replays, reduced motion hides nothing, no part's box moves and the visitor's place holds as content arrives above, a phone never widens, nothing is drawn before it is marked, focus and print see every part, and the empty panels that hold the titles' place never land.

### Fonts

The display font is Dela Gothic One, by the Dela Gothic Project Authors. The body font is M PLUS Rounded 1c, by the Rounded M+ Project Authors. Both are self-hosted from `web/public/fonts`, so visitors' browsers never contact Google. `npm test` builds the production bundle in memory and fails if any file in it references Google Fonts.

The files are subsets with Latin letters, kana and the star symbol, about 100 KB for all three. Kanji fall back to a system font. They load with `font-display: optional`, and `index.html` preloads all three, so they come before the page first draws its text: a font that comes later is left out until the next visit, as swapped in it would move the page. `web/e2e/list.e2e.ts` checks both: nothing on My List moves with the fonts held till it has drawn, and a cold visit 40 ms from the server draws in the page's own fonts. Both fonts use the SIL Open Font License, and `web/public/fonts/OFL.txt` carries their copyright notices.

### Browser checks

`web/e2e` holds checks that run the real page in headless Chrome: layout and layout shift on desktop and phone, keyboard use, the section links, the scroll slam, title addresses, reduced motion, Windows contrast themes, the title card and its trailer, search, the pull, trending refreshed while it is on screen, what a visitor sees when AniList is down, My List's page at `/list`, and the component gallery. Two more check AniList's API itself. They need no extra package. Node drives Chrome over its DevTools protocol.

To run them, start the app with `npm run dev`, then point `CHROME_BIN` at a Chrome or chrome-headless-shell binary:

```bash
CHROME_BIN="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" npm run test:browser
```

A run takes about 20 minutes. The app waits a minute before retrying a failed connection, and the outage checks wait that minute out on the page's own clock, stopped and moved on by the check, so they take seconds, not two minutes.

#### Recorded answers

Every check but the two live ones gets AniList's answers from `web/e2e/anilist/`, not from its API. A run would otherwise send AniList about 30 requests, 22 of them in its first minute, against its limit of 30 a minute for each IP address. Each file there holds AniList's real answer to one request the checks send, recorded by `npm run e2e:record`. `web/e2e/browser.ts` answers each request in Chrome with a copy of its recording, 200 ms after the page asks, about as long as AniList takes to answer. Chrome can't even look up AniList's address, so a request that got past the recordings would fail before it reached AniList. No browser's Chrome, live or recorded, can look up YouTube's or Google's addresses either (`GOOGLE` in `browser.ts`), so a check that presses Watch trailer sees the page ask for the embed, and nothing reaches YouTube.

The recordings are [AniList](https://anilist.co)'s data. The folder holds only the 26 answers the checks ask for, about 3.5 MB of JSON (AniList's answers as they came, every tag of each title), with no images and no user data. Only the checks use it. `npm test` builds the production bundle in memory and fails if any code or file in it came from `web/e2e/`, whether an import, a glob or an alias brought it in, or a stylesheet or `index.html` named it. A second check reads the code in `web/src` for a path into `web/e2e/` and names the line it finds.

Some checks stage answers AniList rarely gives, such as a refused request or titles all tagged Ecchi. `browser.ts` rewrites the answer before the page sees it, whether it was recorded or came from AniList. A rewrite can send headers too, such as a 429's `X-RateLimit-Reset` a second away, so that the app tries again a second later rather than a minute.

#### Recorded, live or off

`ANILIST` sets where the answers come from:

| `ANILIST`            | Answers come from                             | Requests to AniList's API in a run |
| -------------------- | --------------------------------------------- | ---------------------------------- |
| `recorded` (default) | the recordings, except in the two live checks | 2                                  |
| `live`               | AniList, unless a check asks for recordings   | about 30, 22 in the first minute   |
| `off`                | the recordings, and the two live checks skip  | none                               |

```bash
ANILIST=live CHROME_BIN="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" npm run test:browser
```

Run `ANILIST=live` on its own, while nothing else on the machine uses AniList. A live run tests this week's titles. The recordings keep the titles from the day they were recorded. Under `ANILIST=off`, a check that asks for a live browser fails, so a new one must skip under `off`, as the live checks do.

#### Recording again

Run the recorder in `web/` with `npm run e2e:record`, or from the root with `npm run e2e:record --workspace web`. It sends AniList one request at a time, at least 6.5 seconds apart, so never more than 10 in a minute. All 22 take about two and a half minutes. By default it records only the missing and stale recordings, and deletes any that no check asks for. `npm run e2e:record -- --all` records every one again, and `npm run e2e:record -- trending search-frieren` records just those two, by file name. It prints a line for each recording saying what changed.

Record again when:

- `npm test` says a recording is missing or stale. A recording goes stale when the app changes the request it answers, in its query or its variables. Asking for one more field of every title makes all 22 stale.
- A check sends a request that has no recording. The check fails, naming the request and saying how to record it. Add the search to `SEARCHES`, the decade to `DECADES`, the id of a title opened at its address to `TITLES`, or the ids My List asks for to `LISTS`, in `web/e2e/recordings.ts`, then run the recorder. `list-12` there is AniList's real answer for 12 saved ids; `web/e2e/list.e2e.ts` builds every other list's answer from titles already recorded, with a rewrite, so most My List checks need no recording of their own. Another kind of request goes in `requests()` there instead, and the message says so. If the request is the start of a search the check typed with `search()`, the page searched mid-word on a busy machine. The message then says to run the check again, with nothing to record. If it is the start of a recorded search, the page may have searched mid-word, and the message says to run the check again first.

The recorder writes nothing unless every answer is a 200 with no errors and the titles still hold what each check relies on, such as Frieren first in a search for "frieren". If AniList's titles can't hold it any more, the recorder says which check relies on it. That check must change, and so must its rule in `RULES` in `web/e2e/recordings.ts`.

Keep `SEARCHES`, `DECADES`, `TITLES` and `LISTS` up to date by hand. When a check stops sending a search, take it out of `SEARCHES`, with any rule for it, and the recorder deletes its recording. Nothing else notices a recording that no check uses any more.

A new check that needs something particular of a title, such as a banner or a long name, should stage it with `rewriteAniList` in `browser.ts` instead of counting on a recording to have it.

#### Covers

Covers and banners still load from AniList's image server in every mode, so the checks need the internet. Three checks depend on those images:

- "on a 2x screen, decade covers load AniList's 460px file where there is one" waits for the first two 1990s covers to load.
- "the splash panel shows its cover when the window narrows, even after its banner failed" waits for the first sample title's cover to load.
- "every trending panel shows a brand-hot focus ring when tabbed to" counts brand-hot pixels in screenshots that take in the covers.

AniList replaces covers now and then, and an old file can disappear. A cover that can't load doesn't show, and its panel shows the title's color instead. If one of the first two 1990s covers in the recordings has gone, the first of these checks fails with "the first decade covers never loaded". `npm run e2e:record -- --all` records the answers again, with the covers' current addresses. The splash panel's cover belongs to a sample title, so `npm run samples` in `web/` refreshes it instead.

#### The two live checks

`web/e2e/live.e2e.ts` has the app send AniList's API two of its own requests: a first visit's one request for trending and the 1990s, then a search for the first trending title by its name. A run sends AniList these 2 requests and a CORS preflight, and one more of each when the first-visit check asks again (see below). The checks judge AniList's answer as it came over the network, by the rules in `web/e2e/live.ts`:

- While AniList's API is down or busy, they skip, saying why and that it's not the app. That covers a 429, a 403, no connection, no answer within 20 seconds, a 5xx that a one-line health query confirms, and a first visit's trending or 1990s list sent empty twice, with nothing else wrong. Node's test runner lists each skipped check with its reason. While the live checks skip, nothing checks AniList's API, so look out for skips.
- When AniList answers in a way the app can't use, they fail, in AniList's words when it gave some. That covers a query it turns down, a missing field, a field in a format the app can't read, and CORS headers that keep the answer from the page.
- They also rely on AniList's data: enough trending and 1990s titles for the page to show, 1990s titles from the 1990s, and a search that finds the title it searched for. If the data breaks one of these, they fail with "That's AniList's data, not its API or the app". If it lasts, every run fails until AniList's data or the rule in `live.ts` changes.

AniList always has trending and 1990s titles, but while busy it can send a list of them empty. Twice, AniList took about 13 seconds to answer a first visit and sent no trending titles, and a run 2 minutes later passed. So when either list comes back empty, and nothing else is wrong with the answer, the first-visit check asks once more, 20 seconds later, from a fresh first visit. If the second answer has the titles, the check goes on with it, and its output says that AniList's first answer was empty. If a list comes back empty again, with nothing else wrong, the check skips: "AniList answered the app's first-visit request twice, 20 seconds apart, with no titles in data.trending.media, a list it always fills: it isn't answering in full right now. It's not the app." An empty list with anything else wrong in the answer, such as a cover over http, fails at once, naming all of it: AniList being busy doesn't explain the rest. A list with some titles, but fewer than the page shows, still fails at once as AniList's data. Before changing a rule for it, run the checks again.

### Tailwind CSS v4 and custom CSS

Tailwind v4 is configured in CSS, not JavaScript. `web/src/styles/index.css` imports Tailwind and holds the design tokens. There is no `tailwind.config.js` or `postcss.config.js`; the `@tailwindcss/vite` plugin handles everything.

Tailwind makes a utility of any word that names one in the files it reads, even in a comment, and by default it reads every file. So `index.css` imports it with `source(none)` and names what it reads: `web/src` and `web/index.html`, but not the tests, the prototypes or the gallery (the browser checks and the scripts sit outside `web/src`). Reading everything, it had shipped about 600 bytes of rules no page used. `npm test` checks this with canaries, utility names written only in files Tailwind mustn't read, such as `italic` in `privacy.test.ts`: none may have a rule in the production stylesheet. The other way round, every Tailwind class the app's markup uses must have its rule there, and every one of the app's own `ab-` and `is-` classes a rule in its stylesheets, so a misspelt class fails.

Tailwind v4 uses native CSS cascade layers, ordered `theme → base → components → utilities`. A later layer wins regardless of selector specificity, so no `!important` is needed. One rule to remember: **put custom component styles inside `@layer components`**. CSS written outside any layer beats every utility class, so a utility like `p-4` would stop working on that element.

### Firebase config is not secret

The `VITE_FIREBASE_*` values identify the Firebase project and are visible in every Firebase website's code. Security comes from Firebase security rules and server-side token checks, not from hiding these values.
